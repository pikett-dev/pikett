# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/). While the version is 0.x, a minor release can change settings or the database schema; this file says how to upgrade.

## Unreleased

- **The web pages show the release** next to the brand in the header (`Pikett · Acme v0.6.3`), read from `pyproject.toml`, which the image keeps at `/app`. A release that cannot be read is left out. `/health` still reports the commit as `version`.
- **Fix: the shell scripts are executable.** `deploy/runner/install.sh`, `deploy/host-agent/install.sh`, `deploy/ops-server/provision.sh`, `deploy/app-host/agent.sh` and six more had mode 644, so the commands in the docs (`ssh root@app-1 /opt/ops-collect-src/install.sh`) failed with "Permission denied" after an `rsync` of a checkout. A test checks that every tracked file with a shebang is executable.
## 0.6.3 - 2026-11-18

No settings or schema changes. Deploy the release. For the container names of Coolify services, update the collector on each server (`/opt/ops-collect-src/install.sh`, see `deploy/host-agent/README.md`); the image-check fix needs only the deploy.

- **Container names of Coolify services:** the containers of a service (a compose stack) share one `coolify.resourceName`, so the collector names them `<resource>/<service>` (`wp1/mariadb`) instead of merging them under one name.

- **Fix, image check:** with Docker's containerd image store, images built on the server have a `RepoDigests` entry and were asked for at the registry, which answers 401. A registry that answers `insufficient_scope` to a valid anonymous token (unknown or private repository; Docker Hub also says this for an unknown tag) now counts as "built locally or private" instead of an error line. A rejected or empty token, a 404, a 429 and every other failure stay errors.

## 0.6.2 - 2026-11-17

No settings or schema changes. Deploy the release; vmalert loads the new rule within 30 seconds. Nothing else is required.

- Docs: README, `docs/operating.md`, the install guide and the READMEs under `deploy/` match 0.6.1 again, after an audit against the scripts and the code. The ones that would have stopped an installation: the install guide's Option B needs `deploy/vmalert/rules.live/` before `compose up`; Option A keeps its configuration files on your machine (a later `provision.sh deploy` overwrites edits made on the server); `provision.sh join` needs `TS_AUTHKEY` and `lockdown` closes public SSH; app servers are tagged before the broad tailnet rule goes; `agent.sh` needs `TEST_HOST`, `HOST_NAME` and `OPS_HOST` (its defaults name `app-1`); the collector needs `TRIVY_SERVER` and `TRIVY_TOKEN`, and its default kinds already include CrowdSec and Lynis. Also: the heartbeat works with any push URL (Uptime Kuma, healthchecks.io), the full list of configuration files, which releases need `provision.sh pipeline` again, the new settings in the README table, and the README line on where Pikett runs.
- Docs: the German button names in `ops-service.env.example` are English now, and `ops-deploy.sh` points to the right CHANGELOG section.
- **Fix: the heartbeat URL no longer reaches the service log.** Its token (a healthchecks.io or Uptime Kuma push URL) was logged by httpx at INFO on every ping, and the error message of a failed ping carried the URL too. httpx and httpcore log at WARNING now, and a failed ping logs its status without the URL. If your container logs go somewhere other people can read them, replace the token of the monitor.
- **New alert `AppHostSilent` (P1).** With several app servers, `AppServerSilent` fired only when none of them sent metrics. `AppHostSilent` names a host that was seen in the last 24 hours and has sent nothing for 3 minutes, while at least one other host still reports (when none does, `AppServerSilent` covers it). A host you remove on purpose raises it for up to 24 hours, and so does the old name after you correct `HOST_NAME`; mute the incident in Slack. vmalert loads the rule within 30 seconds of the deploy, no setting is needed.
- **Fix: `dev/alert.sh` works against a server that needs the token, and on Linux.** `ALERT_TOKEN_FILE=deploy/ops-server/alert-token` reads the token from the file, so it never shows up on screen or in a shell history (before, only `ALERT_TOKEN` or the local dev stack worked, and a remote `OPS_URL` got a 401). The script also runs with GNU `date`, so you can use it on the ops server.

## 0.6.1 - 2026-11-17

No settings or schema changes. Deploy the release; for the container names, update the collector on each server (`/opt/ops-collect-src/install.sh`, see `deploy/host-agent/README.md`).

- **Fix: a missing mailer is no failed patch run.** unattended-upgrades logs "No /usr/bin/mail or /usr/sbin/sendmail, can not send mail" at ERROR level after the upgrade when `Unattended-Upgrade::Mail` is set but the host has no mailer. That opened a P1 `PatchFailed` although the patches were installed. The line is ignored now; to stop it at the source, unset `Unattended-Upgrade::Mail` on the host.
- **Fix: one odd backup run no longer makes the whole database unreadable.** The Coolify API sends `size: null` for a dump that is still running; that execution, or any one that does not parse, is skipped. Only a database whose executions are all unreadable raises `BackupCheckFailed`.
- **Fix: the "Vulnerabilities" card on the overview** takes its freshness from the newest scan (`last_seen_at`) instead of showing "No run yet", turns overdue after 26 hours without a scan, and asks for action while any finding is actively exploited (KEV).
- **Container names:** the collector sends the Coolify resource name (`coolify.resourceName`) for a container that has the label, so Trivy and image lines name the app instead of a UUID with a deploy timestamp. Containers without the label keep their Docker name. Two containers of one resource under one image appear once.
- Docs: `deploy/host-agent/README.md` explains why Coolify's own root logins show up as unusual and how to list its key in `SSH_KNOWN_KEYS`.

## 0.6.0 - 2026-11-17

Upgrade, in this order: (1) `provision.sh pipeline` once, to install the new `ops-deploy` on the ops server (the server holds a copy of it; the old one does not build the rules folder that compose now needs, so `compose up` fails instead of starting vmalert without rules); (2) deploy the release; (3) `agent.sh deploy` on each app server, because its Compose file changed (Alloy now runs on a folder). If you edited the shipped `deploy/vmalert/rules/*.yml`, move those edits into `rules.local/` (same file name replaces the shipped file) before you deploy, or the next checkout overwrites them. Nothing else is required: without your own rules, Alloy files or Postgres the behaviour is the one of 0.5.2, plus the Postgres rules, which stay silent without Postgres metrics.

- **Your own alert rules.** `deploy/vmalert/rules.local/` (git-ignored) holds the rules of an installation. `ops-deploy` puts the shipped rules of the release and these together into `deploy/vmalert/rules.live/`, which vmalert now mounts read-only (compose fails when the folder is missing). A file in `rules.local/` with the name of a shipped file replaces it; with `groups: []` it switches that file off. Before the checkout, `vmalert -dryRun` checks the shipped rules of the target release together with yours; if it refuses them, `ops-deploy` exits with 1 and changes nothing. An empty or missing `rules.local/` is fine.
- **Sending the rules from your configuration repository.** `ops-deploy` accepts `<release> rules` as the SSH command with a tar on stdin (`tar -C rules -cf - . | ssh deploy@<ops-server> "v0.6.0 rules"`) and replaces `rules.local/` with it. At most 1 MiB and 100 entries, only plain top-level `*.yml` files; anything else refuses the whole tar before anything changes. The key can still run only `ops-deploy`. `deploy/ci/*.example.yml` send a `rules/` folder when it exists. `provision.sh deploy` no longer deletes `rules.local/`, and `dev/compose.sh` builds `rules.live/` too.
- **Your own Alloy files.** Alloy now runs on the folder `/opt/ops-agent/alloy/` and loads every `*.alloy` file in it as one configuration, so `local-*.alloy` files can use the components of `config.alloy`. `ALLOY_LOCAL_DIR=<folder> agent.sh deploy` copies the `local-*.alloy` files of that folder (anything else in it is refused) and removes the ones that are gone; without the variable the server keeps what it has. Secrets for these files (tokens, database passwords) come from `/opt/ops-agent/secrets.env` on the app server (mode 600, optional, never written or deleted by `agent.sh`), read with `sys.env`.
- **Examples** in `deploy/app-host/alloy/examples/`: `local-app-metrics.alloy` (an app's `/metrics` behind a Bearer token over the Docker network `coolify`, with `job`, `service` and `host` labels) and `local-postgres.alloy` (`prometheus.exporter.postgres`, one component per database, DSN from the env file).
- **Postgres rules** in `deploy/vmalert/rules/postgres.yml`: `PostgresDown`, `PostgresConnectionsHigh` (above 80 % of `max_connections` for 10 minutes), `PostgresDeadlocks`, `PostgresLongTransaction` (open longer than 10 minutes) and `PostgresExporterFailing`. The monitoring role needs `pg_monitor` and nothing else (`docs/operating.md`, "Your own rules and scrape targets"). The analyst needs no change; its metric tools take any query.
- **Tests:** the new parts of `ops-deploy` and `agent.sh`, `vmalert -dryRun` over all shipped rule files, `alloy validate` over `config.alloy` and the examples together (needs Docker, like the other tests), and a check that compose refuses to start vmalert without `rules.live/`.

## 0.4.0 - 2026-11-16

One upgrade note first: update the ops service and every runner together (the catalog digest changes).

- **The shipped catalog allows the two Coolify runbooks (`container_restart`, `redeploy_previous`) on any server** (`hosts: ["*"]`, was `["app-1"]`), so an installation needs no catalog of its own just to name its servers. Which servers get jobs at all is decided by `RUNNER_TOKENS`, and the application of such a job must be on that server's `RUNNER_APPLICATIONS` list; both were checked before and still are. **Upgrade: the catalog digest changes (`hosts` is part of it), so update the ops service and every runner together, or the runner rejects the jobs of the other side.** The runner no longer rejects these two runbooks by server name; what stops a job on a runner without Coolify is its own `COOLIFY_APPS` allowlist (empty by default, so it fails closed) and the scope of its Coolify token, so list `RUNNER_APPLICATIONS` only for servers whose runner has Coolify. The analyst's prompt names only servers with an application list for these runbooks. An installation that wants the old restriction keeps it in its own catalog (`CATALOG_FILE`, 0.3.0), whose `hosts` it sets as before. Do not approve a reboot or other action while the service and a runner are on different versions: a job rejected for the wrong digest is not retried.

## 0.3.0 - 2026-11-16

Your own runbook catalog is configuration now. Nothing is required on upgrade; installations that keep the shipped catalog behave as before.

- **Upgrade notes.** `docker compose up` creates the empty folder `deploy/ops-server/catalog/` next to `compose.yml` (it is git-ignored). To use your own server names, texts or risk levels, put your edited copy of `runner/catalog.json` there as `catalog.json` and restart the service. Install the same file on every runner with `ssh root@<server> CATALOG_FILE=<path on the server> .../deploy/runner/install.sh`; it is checked first and kept in `/etc/ops-runner/catalog.json`, so later runs of the script leave it in place. Update the runner code on a server (rsync and `install.sh`, as in `deploy/runner/README.md`) before you rely on this there: the runner reads `/etc/ops-runner/catalog.json` only from this version on.
- **New setting `CATALOG_FILE`** (default `/etc/pikett/catalog.json`, the path compose mounts the folder to). The service uses the file when it exists and otherwise `runner/catalog.json`. A file that cannot be read or parsed stops the start with a message that names the path; so does a `CATALOG_FILE` you set yourself that points to a missing file; a folder with other files but no `catalog.json` is logged as a warning. The runner follows the same rule through the `CATALOG_FILE` of its environment (default `/etc/ops-runner/catalog.json`), implemented once in `runner.catalog.load_installed_catalog`.
- Every runner needs a catalog with the same security fields as the service, because the digest signed into each job covers `risk`, `hosts`, `verify` and the parameter rules. Texts and `proposable` are not part of it; keep `proposable` equal by hand. README section "Runbook catalog".

## 0.2.0 - 2026-11-16

Launch hardening. Upgrade notes first:

- **Before the next deploy, in this order:** (1) create `deploy/ops-server/alert-token` on the ops server, (2) if you deploy with the pipeline, run `provision.sh pipeline` again (with `OPS_REPO_URL`, see below) so the server's copy of `ops-deploy.sh` is the new one, (3) deploy. The compose file mounts the token file into vmalert, and `docker compose up` stops with a missing-file error without it; only the new `ops-deploy.sh` checks for it before it builds. Generate a token with `openssl rand -hex 32`, set it as `ALERT_TOKEN` in `.env` and write the same value to `alert-token` (mode 600, git-ignored, as are all `*-token` and `*.token` files). `provision.sh deploy` writes the file from `.env` for you. `ops-deploy.sh` refuses to deploy when the file is missing or differs from `.env` (after a rotation, update both). An empty `ALERT_TOKEN` and an empty file keep the old behaviour (open webhook) and the service logs a warning at startup.
- **New setting `ALERT_TOKEN`** (at least 32 characters, different from the runner and host-report tokens). When set, `POST /api/v2/alerts` needs `Authorization: Bearer <token>` and answers `401` otherwise (compared in constant time, the presented value is never logged). vmalert sends it through `-notifier.bearerTokenFile`, so it does not show up in `ps` or `docker inspect`. `dev/alert.sh` sends it when `ALERT_TOKEN` is set, or reads it from `dev/dev.env` for the local stack.
- **Request size limits.** Alerts: at most 100 per request, 64 labels and 64 annotations per alert, keys up to 256 characters, values up to 16 KB, `generatorURL` up to 2048 (`422` otherwise). Request bodies: alerts 1 MB, host reports 4 MB, runner calls 256 KB (`413`, also for chunked bodies without `Content-Length`).
- **Collector: Trivy reports are capped** at the most severe findings: 200 per image, and at most 5000 per report, shared equally when a server runs more than 25 images (`ops-collect.py`, update it on every server). The report says how many were left out and the daily summary names the images that were cut. Without the cap a busy server could exceed the 4 MB report limit.
- **Container hardening.** `ops-service` runs with `read_only: true`, `cap_drop: [ALL]` and `no-new-privileges`, with a 64 MB `/tmp` in memory and a new volume `osv-work` (`HOME` and `TMPDIR`) for the OSV scan. Alloy still runs `privileged` (Grafana documents no other setup for cAdvisor in a container); `deploy/app-host/README.md` says what that means and how to undo the install.
- **Tailnet policy example** `deploy/tailscale-acl.example.hujson`: tags `tag:pikett-ops` and `tag:pikett-app`, group `group:pikett-team`. The web UI and the Victoria ports have no login of their own; the tailnet policy is their access control. `provision.sh join` now advertises `tag:pikett-ops` by default (was `tag:server`; set `TS_TAGS` to keep the old one). Once the policy is in place, `deploy/app-host/agent.sh status` asks the ops server from the app server, because laptops no longer reach the telemetry ports.
- **Images pinned by digest** in all compose files and the Dockerfile, GitHub Actions pinned by commit SHA (checkout v4.4.0, setup-uv v6.8.0), the gitleaks image by digest, `permissions: contents: read` per CI job, and `uv` in the Dockerfile updated from 0.7.5 to 0.13.8. Renovate keeps the pins current (`docker:pinDigests`, `helpers:pinGitHubActionDigests`).
- **`provision.sh pipeline` needs `OPS_REPO_URL`** (an SSH URL such as `git@github.com:pikett-dev/pikett.git`); the old default pointed to a placeholder Bitbucket repository. The host key and SSH config entry on the server now use the host of that URL instead of `bitbucket.org`, and the known-hosts file is `/root/.ssh/known_hosts_repo`. Run `provision.sh pipeline` again to refresh the server.
- Settings missing from the examples are in `ops-service.env.example` now: `SSH_KNOWN_USERS` (list every user your CI or deploy pipeline logs in with, or each deploy raises an SSH alert), `SSH_ANY_TIME_USERS`, `LOG_LEVEL`.
- Docs: README sections "Data that leaves your servers" and "Operating Pikett", the terms table in "How it works", `docs/operating.md` (upgrade, backup and restore of `ops-db`, uninstall), an "Undo" section for Alloy, and the tailnet policy step in the install guide.
- **SSH review knows keys by fingerprint.** New setting `SSH_KNOWN_KEYS` (JSON: label, fingerprint, user, networks, optional hosts). A login that matches a known key is usual at any time; any other unusual login goes out as one grouped message per report and server (by source, user and key); an unknown key, or a known key from the wrong user or network, is posted per group (at most 5 per report, the rest in one more message). Without keys the review judges by network, user and time as before. Upgrade note: the posted-login key now includes the fingerprint, so logins of the last 3 days may be posted once more after the update.
- README: alert flow diagram (`docs/assets/pikett-flow*.svg`) and a Mermaid architecture diagram instead of the ASCII sketch.

Upgrade notes first, then the rest.

- **Renamed from ops-core to Pikett.** Python package `pikett`, Docker image `pikett:latest` and `pikett:<sha>` (built by `ops-deploy.sh` and `provision.sh`), compose projects `pikett` (local Postgres) and `pikett-stack` (local all-in-one stack), web UI brand "Pikett" (or "Pikett · <PROJECT_NAME>", which replaces "<PROJECT_NAME> Ops"), Slack app and bot name "Pikett". Local development: a new compose project name means new volumes, so the local databases start empty; the data stays in the volumes of the old project names.
- **Ops server: update `OPS_IMAGE` and the deploy script before the first deploy.** Set `OPS_IMAGE=pikett:latest` in the server's `.env` (`provision.sh deploy` does it) and reinstall the pipeline script (`provision.sh pipeline`). With the old `.env` and the new script, compose keeps running the old image while the deploy looks green.
- **Runner and service must be updated together.** The signing prefix of runner jobs is now `pikett-job-v1`. A runner and a service on different sides of this change reject each other's jobs.
- **New settings `LANGUAGE` and `TIMEZONE`.** `LANGUAGE` is `en` (default) or `de` and sets the language of the web UI, Slack messages, ntfy pushes, reports, alert summaries, runbook texts and the AI analysis. `TIMEZONE` is an IANA name (default `UTC`; an unknown name stops the start with a message). It replaces the fixed Vienna time everywhere: displayed times, the time of the daily digest and the weekly report, the day of the AI budget, the on-call week, SSH quiet hours and the reboot window. To keep the behaviour of the first release set `LANGUAGE=de` and `TIMEZONE=Europe/Vienna`. Changing `TIMEZONE` in the middle of a day can shorten or lengthen the AI budget day once, and the digest of that day may run twice or not at all. Set it to the zone your servers use: their patch logs are read in it.
- **English is the default language.** Every user-facing text moved into message catalogs (`app/i18n/locales/en.json`, `de.json`). The German texts are unchanged. Text that the service wrote into the database earlier (incident summaries, errors of analyses and actions, backup problems) stays German, and new text is written in the configured language. The error texts of the collector on the app servers (`ops-collect`) are English only, because it does not know `LANGUAGE`.
- **English URL paths.** `/ops/verlauf` is now `/ops/history`, `/ops/hilfe` is `/ops/help`, `/ops/aktionen/{id}` is `/ops/actions/{id}`. The history filters are `kind`, `status`, `host` and `period` (were `art`, `status`, `server`, `zeitraum`). The old paths answer `301` and keep the query string, mapped to the new names, so links in old Slack messages still work.
- **Runbook catalog schema.** `title`, `description` and `rollback` in `runner/catalog.json` are objects per language (`{"en": "...", "de": "..."}`, English required). A catalog with plain strings is refused at load. The texts are not part of the catalog digest, so jobs signed before the update stay valid.
- The overview of the checks no longer guesses from the wording of a report line whether it needs action. The checks flag it (`app.security.lines.Line`); lines without a flag are still recognised by their old markers, in German and in English.
- Favicon and icon in the web UI (`/static/`). The Slack app icon cannot be part of the manifest; the install guide says where to upload `docs/assets/pikett-icon-512.png`.
- Installation guide for AI coding agents (`docs/install-with-an-ai-agent.md`).

### Unchanged on purpose

So that installed servers keep working: the component names `ops-service`, `ops-runner` and `ops-collect`, the directory `/opt/ops`, the systemd units and timers, the `OPS_*` environment variables, the `ops-fix/` branch prefix and the compose project `ops` of the ops server. The timers and cloud-init files in `deploy/` still say `Europe/Vienna`; change them together with `TIMEZONE` if your servers use another zone.

## 0.1.0

First public release, extracted from a production installation.

- Alerting: Alertmanager v2 webhook, one incident per alert, Slack threads with buttons, ntfy paging with escalation, weekly on-call rotation, reminders, watchdog, daily digest and weekly report.
- AI analysis: read-only tools for VictoriaLogs, VictoriaMetrics and VictoriaTraces, drain3 log templates, recent deploys with commits and diffs, PII masking, evidence-checked structured output, three model stages with a daily budget, incident memory and feedback.
- Actions: Ed25519-signed runbook jobs pulled by a sandboxed runner, Slack approvals, health verification, fix pull requests that are never merged automatically.
- Security: patch window with needrestart, reboot approvals, Trivy and OSV findings, CISA KEV and EPSS, image updates, Coolify version, Lynis, CrowdSec, SSH logins, backup checks.
- Web UI for checks, history, incidents and actions.

New settings compared with the internal version: `PROJECT_NAME`, `AGENT_STACK_DESCRIPTION`. The signing prefix of runner jobs is new compared with the internal version; runners and the ops service must run the same version.
